# Codex レビュー（codex-review）

ベースブランチから分岐したあとの未レビューのコミットを **Codex にレビューさせ**、返ってきた指摘を
あなた（このスキルを実行しているエージェント）が**実コードで検証**し、妥当性の判断と修正方針を
ユーザーに提示する。**修正の実装はユーザーの承認後に行う。**

## 役割分担（厳守）

| 主体 | 役割 |
|---|---|
| Codex | レビューして指摘する。**コードは修正しない**（read-only サンドボックスで起動） |
| あなた | 指摘の妥当性を検証し、修正方針を提示する。**承認後に修正を実装する** |
| ユーザー | どの指摘を修正するかを決定する |

作成者とレビュー担当を分離するのが目的である。あなたが実装した変更をあなた自身のレビューだけで
承認しない。同時に、Codex の指摘も鵜呑みにしない。

---

## 言語

ユーザーへの出力・問いかけは、ユーザーが使っている言語で行う（既定は日本語）。
Codex の出力言語は `--lang`（既定 `ja`）で決まる。ユーザーが別の言語を使っている場合は
`--lang en` などを付けて実行してよい。

---

## 実行するコマンド

レビューは同梱の CLI `codex-review` で行う。

1. `codex-review` が PATH にあればそれを使う（`command -v codex-review` で確認）
2. 無ければ、**このスキルのディレクトリ**にある `bin/codex-review` を絶対パスで実行する
   （例: `~/.claude/skills/codex-review/bin/codex-review`）

以下、どちらの場合も `codex-review` と表記する。CLI は自分の案内（完了コマンド等）を、
実際に動く形（コマンド名か絶対パス）で表示する。表示されたものをそのまま使うこと。

## 手順0: 引数の解釈

ユーザーが渡した引数（Claude Code なら `$ARGUMENTS`。無ければ依頼文から読み取る）を
そのまま `codex-review` に渡す。

| 引数 | 意味 |
|---|---|
| (なし) | ベースとの差分のうち、未レビューのコミットをレビュー |
| `--base <ref>` | 比較するベースブランチを変える |
| `--dirty` | 未コミットの作業ツリー差分も含める |
| `--force` | レビュー済みのコミットも再レビューする |
| `--status` | 記録済みコミットの一覧を表示して終了する |
| `--complete <sha>...` | 指摘を提示し終えたコミットをレビュー済みとして記録して終了する（手順4.5 で使う） |
| `--model` / `--effort` | Codex のモデル・推論強度を指定する。成功後は既定として記憶される |
| `--lang <lang>` | Codex の出力言語（既定 `ja`） |
| `--reset-defaults` | 記憶したモデル・推論強度を消して終了する |
| `--dry-run` | 依頼ファイルとプロンプトを作るだけで Codex を起動しない |

ユーザーが「もう一度レビューして」「同じコミットを再レビュー」と明示した場合のみ `--force` を付ける。
自動で付けてはならない（レビュー済みを除外するのがこのコマンドの既定動作のため）。

## 対象コミットの決め方

```
（ベースブランチとの分岐点から HEAD までの全コミット） − （レビュー済みとして記録済みの SHA）
```

範囲を絞る引数（`-n` や `--range`）は無い。途中のコミットだけ未レビューで残る状態を作れてしまい、
「レビュー漏れを防ぐ」という目的と矛盾するため。ブランチ上の未レビューのコミットは常にすべて対象になる。

ベースブランチは次の順で決まる。CLI は実行時に「ベース: X [出所]」と表示するので、
意図と違うベースになっていたらユーザーに伝える。

1. `--base <ref>`
2. 環境変数 `CODEX_REVIEW_BASE`
3. `git config codex-review.base`（リポジトリごとの既定。例: `git config codex-review.base origin/develop`）
4. 自動判定: `origin/HEAD` が指すブランチ → `origin/main` → `origin/master` → `main` → `master`
   （現在のブランチ自身は除く）

ローカルのブランチや `origin/HEAD` が古いと、取り込み済みの上流コミットまで「未レビュー」に見える。
対象件数が想定より大きい場合は `git fetch` と `git config codex-review.base` の設定を提案する。

## レビュー済みコミットの管理

同じコミットを何度も Codex にレビューさせないため、SHA を `.git/codex-review/state.json` に記録する
（`.git` の中なのでコミットされない。ワークツリー間で共有される）。

- 記録するのは、**あなたが指摘をユーザーへ提示し終えたコミットだけ**（手順4.5 の `--complete <sha>...`）。
  Codex の実行が成功しただけでは記録しない。提示前に中断されれば何も記録されず、次回また対象になる
- 記録できるのは、実際にレビューを通した SHA だけ。レビュー成功時に「提示待ち」として積まれ、
  `--complete` はそこに載っている SHA しか受け付けない
- コミットの内容は不変なので記録は SHA をキーとする。指摘を修正して新しくコミットすれば、
  それは別 SHA なので次回のレビュー対象になる
- 状態ファイルが壊れている場合は「未レビュー」に倒れる（再レビューが増えるだけで、レビュー漏れは起きない）
- 状態ファイルの更新はファイルロックで直列化している（並行実行しても更新が失われない）

CLI が「レビュー済みの N 件を除外し、未レビューの M 件をレビューします」と出力した場合は、
その内容をユーザーに伝えてからレビュー結果を提示する。

---

## モデル・推論強度の記憶

`--model` / `--effort` は、**レビューが成功した時点で既定として記憶**され、次回以降は指定を省略できる
（`.git/codex-review/prefs.json`）。

- `--model` と `--effort` は独立して記憶される
- **失敗した実行では記憶しない**（起動できないモデルを既定にすると、以降のレビューが黙って全部失敗するため）
- `--dry-run` は記憶しない
- 実行のたびに、使うモデル・推論強度とその出所が表示される
- 記憶を消すのは `--reset-defaults`。ファイルを手で編集しない

記憶した既定が使われた場合は、その旨もユーザーに伝える。

---

## マージコミットの扱い

マージコミットも**レビュー対象に含む**（競合解消は作成者が手で書いた差分であるため）。
差分は `git show --remerge-diff`（自動マージ結果との差分）で出し、**手作業の競合解消だけ**を提示する。

- 競合のないマージは「手作業による競合解消は含まれません」と表示され、ノイズにならない
- `--remerge-diff` が使えない環境（git 2.36 未満）では**中止する**（exit 1）。
  ユーザーに **git の更新**を案内する。暫定回避として `--base <そのマージより後の ref>` で範囲から
  外せるが、それ以前のコミットも対象外になるため恒久策にはしない

## プロジェクト固有のレビュー基準

リポジトリ直下に `.codex-review.md` があれば、Codex はそれを最優先のレビュー基準として読む
（場所は `git config codex-review.guide <path>` で変更可）。あなたも手順3・手順5 でこのファイルを読み、
設計書の場所、テストの実行方法、修正時のルールに従う。

## 手順1: Codex レビューの実行

```bash
codex-review <引数>
```

- Codex は read-only で起動するため、リポジトリが書き換わることはない
- 実行前に「Codex のレビューには数分かかる」旨をユーザーに一言伝える

### 実行時間（重要）

推論強度 `high` の環境では、**1コミットのレビューでも 7 分程度かかる**ことがある。

- コマンド実行のタイムアウトを **10分以上**にする（Claude Code なら Bash の `timeout` に `600000`）。
  既定の 2 分では必ず途中で切れる
- 対象コミットが多い場合は、バックグラウンド実行できるハーネスならバックグラウンドで実行し、完了を待つ
- それでも時間切れになる場合は `--effort medium` を付けて再実行し、その旨をユーザーに伝える

### 終了コードの扱い

| 終了コード | 意味 | 対応 |
|---|---|---|
| `0` | 正常終了 | 手順2へ進む |
| `1` | ベースが特定できない・git が古い等 | 出力をユーザーに伝えて**停止**する |
| `2` | 対象コミットが見つからない | CLI の案内をユーザーに伝えて**停止**する。勝手に範囲を広げない |
| `3` | 対象コミットがすべてレビュー済み | 「新たにレビューすべきコミットはない」旨を伝えて**停止**する。勝手に `--force` を付けて再実行しない |
| `127` | codex CLI が未インストール | 下記「codex CLI が無い場合」に従って案内し**停止**する |
| その他 | Codex の実行失敗 | `.git/codex-review/raw.log` の末尾を確認し、原因を報告して停止する。認証エラーの兆候があれば CLI が `codex login` を促すので、それも伝える |

### codex CLI が無い場合（exit 127）

**あなたが勝手に `npm install` を実行してはならない。** グローバル環境への変更はユーザーの判断事項である。
CLI の出力をユーザーに提示し、次を伝えて停止する。

```bash
npm install -g @openai/codex   # インストール
codex login                    # 初回のみ認証
```

あわせて、**codex を入れずに済ませる代替手段**も伝える。`codex-review --dry-run` は codex を必要とせず、
レビュー依頼（`.git/codex-review/request.md`）とプロンプト（`.git/codex-review/prompt.md`）を生成する。
他の AI や人間のレビュー担当へそのまま渡せる。

## 手順2: レビュー結果の読み込み

生成物（いずれも `.git/codex-review/` の中。ワークツリーではワークツリー専用の git ディレクトリの中）:

| ファイル | 内容 |
|---|---|
| `request.md` | Codex に渡したレビュー対象（対象コミットと差分） |
| `prompt.md` | Codex に渡した指示（`--dry-run` 時のみ保存） |
| `result.json` | Codex の構造化レビュー結果 |
| `raw.log` | Codex の実行ログ |
| `state.json` | レビュー済みコミットの記録と、提示待ちの SHA |
| `prefs.json` | 記憶したモデル・推論強度 |

正確なパスは CLI の出力（「レビュー結果: …」）に表示される。`result.json` の構造:

- `summary`: 全体要約
- `findings[]`: `id` / `severity`(blocker\|non-blocker) / `title` / `location` / `detail` / `evidence` / `proposedFix` / `confidence`
- `verified[]`: Codex が確認した内容
- `remainingRisks[]`: 未確認事項

## 手順3: 各指摘の妥当性検証（このスキルの核心）

**Codex の指摘をそのまま転記してはならない。** 指摘ごとに、必ず実際のコードと設計書を読んで裏を取る。

1. `location` のファイルを実際に読み、指摘された箇所が現在のコードに存在するか確認する
2. `evidence` の内容が実際のコードと一致するか確認する（Codex の記憶や推測でないか）
3. 指摘が成立する具体的な条件（入力値・状態・データ）を特定する。特定できないものは「再現条件不明」として扱う
4. 関連する設計書・仕様（`.codex-review.md` に場所の記載があればそこ）と照合する
5. 既存の呼び出し元・テストを確認し、本当に壊れるかを判断する

そのうえで、次の3つのいずれかに分類する:

| 判定 | 意味 |
|---|---|
| **妥当** | 指摘は正しく、修正すべき |
| **部分的に妥当** | 問題は実在するが、深刻度・原因・修正方針が Codex の記述とは異なる |
| **誤検知** | 指摘は成立しない（コードを誤読、既に対処済み、仕様通り 等） |

`confidence` が `low` の指摘、および `evidence` が抽象的な指摘は、特に慎重に裏を取る。
**誤検知だと判断した場合は、その根拠（実際のコードのどこを見てそう判断したか）を必ず示す。**

## 手順4: ユーザーへの提示

以下の形式で提示する。

### 1. 概要

対象コミット（`git log --oneline` 相当）、使ったベース、Codex の指摘件数、うち妥当と判断した件数。

### 2. 指摘一覧（表）

| # | 深刻度 | 指摘 | 箇所 | 判定 |
|---|---|---|---|---|
| F1 | blocker | （Codex の指摘の要約） | `path/file.ts:123` | 妥当 |
| F2 | non-blocker | … | `path/file.py:45` | 誤検知 |

### 3. 指摘ごとの詳細

**妥当**・**部分的に妥当** と判断したものについて、それぞれ:

- **Codex の指摘**: 内容の要約
- **検証結果**: 実際に読んだコード・設計書と、そこから何を確認したか
- **判定と理由**: なぜ妥当（または部分的に妥当）と判断したか
- **修正方針**: 変更するファイルと具体的な修正内容。影響範囲とテストの要否も書く

**誤検知** と判断したものは、指摘内容と却下理由を1〜2行で簡潔に書く。

### 4. 確認事項

Codex の `verified` と `remainingRisks` のうち、ユーザーが知るべきものを簡潔に伝える。

### 5. ユーザーへの確認

修正対象をユーザーに選ばせる。**この時点では絶対にコードを変更しない。**
選択肢は「blocker のみ修正」「全て修正」「個別に選ぶ」「修正しない」を基本とする。

## 手順4.5: 完了記録（提示直後に必ず実行）

手順4 で指摘をユーザーへ提示し終えたら、**その直後に**、レビュー実行の最後に表示された
完了コマンドを**そのまま実行する**（対象 SHA が埋まった形で表示される）。

```bash
codex-review --complete --findings <件数> --blockers <件数> <sha>...
```

- これを実行して初めて、対象コミットが次回以降の除外対象になる
- 記録されるのは**指定した SHA だけ**。並行実行や別セッションの対象を巻き込まない
- ユーザーが修正するかどうかを決める**前**に実行してよい。記録するのは
  「Codex のレビュー結果を提示し終えた」という事実であって、修正の有無ではない
- 実行し忘れた場合は次回同じコミットが再レビューされるだけで、レビュー漏れにはならない
- SHA を指定しない `--complete` はエラーになる。状態ファイルを手で編集しないこと
- レビューを通していない SHA を指定するとエラーになる（何も記録されない）。
  「レビューを通していないコミットは記録できません」と出たら、表示されたコマンドを使い直す
- 一部でも対象外の SHA が混ざっていると、**何も記録しない**
- `--dirty` だけでコミットが 0 件だった実行は「記録は不要」と表示される。この場合 `--complete` は実行しない

## 手順5: 承認後の修正実装

ユーザーが修正対象を確定してから実装する。

### 実装前に必ず読む

- リポジトリの AGENTS.md / CLAUDE.md などのエージェント向けルール
- `.codex-review.md` の「修正時のルール」（過去のレビュー指摘の再発防止ファイル、
  ドキュメント同期のルール、テストの実行方法などが指定されていればそれも）

Codex にはこれらを読ませているのに、修正する側が読まないと意味がない。

### 判定ロジックを直すときは変更前後の表を作る

条件分岐の判定（どれを対象とみなすか、どれを除外するか）を変更する場合、
**指摘された事例だけを確認して終わりにしてはならない。** 入力の集合を固定し、変更前と変更後を並べた表を作る。

| 入力 | 期待 | 変更前 | 変更後 |
|---|---|---|---|
| 指摘された事例 | ... | NG | OK |
| 既に通っていた事例 | ... | OK | **OK であること** |

- 「変更前」の列が無いと退行に気づけない
- 入力集合は過去に扱った事例を**すべて残したまま**足す。減らさない
- 表と同じ集合を回帰テストに落とし、**修正前のコードでそのテストが失敗すること**を確認する
- 検討した代替案が過去の修正を打ち消さないかも確認する

### 実装

- 承認された指摘のみを修正する。ついでの改善・リファクタリングを混ぜない
- コード変更に対応するドキュメントを、プロジェクトのルールに従って同じ作業単位で更新する
- プロジェクトのルールに従ってテスト・lint・型チェックを実行し、結果を報告する。
  実行できない場合は、その理由と、ユーザーが手で流すためのコマンドを併記する
- 修正後、何をどう直したかを報告する
- プロジェクトに再発防止の記録ファイルがある場合は、修正した指摘をそのルールに従って記録する

---

## やってはいけないこと

- Codex の指摘を検証せずにそのまま報告する
- プロジェクトのルール（AGENTS.md / CLAUDE.md / `.codex-review.md`）を読まずに修正を実装する
- 判定ロジックの変更を、指摘された事例だけ確認して完了にする（変更前の列を作らない）
- ユーザーの承認前にコードを修正する
- 承認されていない指摘まで「ついでに」修正する
- 対象コミットが見つからないときに、勝手に範囲を広げてレビューする
- ユーザーの指示なしに `--force` を付けて、レビュー済みのコミットを再レビューする
- ユーザーの許可なく codex CLI をインストールする
- 状態ファイル（`.git/codex-review/state.json`）を手で編集してレビュー済み扱いにする
